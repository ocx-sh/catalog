# CI Renderer Subsystem

`ocx-catalog ci [--check]` generates other repos' CI workflows
(`.github/workflows/catalog-ci.yml` for `github`, `.gitlab-ci/catalog.yml`
for `gitlab` — a job file the repo's own root `.gitlab-ci.yml` includes,
never the root file itself). Its own output must satisfy the security
invariants it's generating, since a consumer trusts this renderer to produce
compliant CI without hand-review of every line.

## Output invariants (never regress)

- **`permissions: {}` at the workflow level**, per-job least privilege
  (`permissions: { contents: read }`) — see `templates/ci/github-ci.yml`.
- **`persist-credentials: false`** on every `actions/checkout` step.
- **SHA-pinned `uses:` refs only.** `pins.ts`'s `COMMIT_SHA_RE`
  (`^[0-9a-f]{40}$`) is the enforcement point: a committed pin that isn't a
  full 40-hex commit SHA (`@main`, `@v4`, a tag) is **never** carried
  forward — the template default (a real SHA, `DEFAULT_PINS`) is used
  instead, and `warnUnusablePins` reports it on stderr. This exists because
  `normalizeForDrift` strips `@ref` before comparing, so without this guard a
  hand-edit from `@<sha>` to `@main` couldn't trip the `verify-catalog-ci`
  job this package itself generates, and the next render would silently
  adopt the mutable ref as the new pin.

## Header-version contract

Every file this renderer writes starts with `HEADER_LINE`
(`# generated by ocx-catalog ci v<N> — do not edit`, `src/ci/header.ts`).
That first line is itself the "is this ours" test — `discoverGeneratedFiles`
(`src/ci/discover.ts`) treats a missing or malformed header as "not ours":
never touched, never scraped for pins, never drift-checked. A discovered
file whose header names a version **newer** than `TOOL_HEADER_VERSION`
throws `CiError("TOOL_TOO_OLD")` — refuse rather than silently
misinterpret a newer contract with an older tool.

Bump `TOOL_HEADER_VERSION` only when the render/discovery/normalize contract
changes in a way an older tool version could no longer safely parse. A file
naming an older version must go on being parsed and scraped for pins
forever — `parseHeaderVersion` has no per-version branching, only the number
in the pattern changes.

## Pin carry-forward

`scrapePins` (`pins.ts`) scans every discovered file's `uses:` lines. An
action pinned identically everywhere it appears is carried forward into the
new render; an action pinned to more than one distinct SHA is a `conflicts`
entry; an action pinned to anything but a SHA is a `mutableRefs` entry. Both
conflict cases fall back to `DEFAULT_PINS` and warn on stderr — the reasons
are reported separately because the fix differs (two files disagreeing vs. a
hand-edit to re-pin).

## `--check` drift semantics

`checkCi` (`src/ci/write.ts`) compares each rendered file against what's
committed through `normalizeForDrift` (`src/ci/normalize.ts`) — **never raw
bytes**. Normalization strips line-ending differences and any `@ref`/trailing
comment off a `uses:`/`image:` line, so a Renovate/Dependabot pin bump on the
committed file is never read as drift; only an actual structural change (or a
different action entirely) trips it. A missing file counts as drift. Any
drift throws `CiError("DRIFT")` naming every mismatched file — exit 65 via
the CLI's `CiError` mapping.

## `packageManager`: closed union, not an open string

`CiConfig.packageManager` (`config/types.ts`) accepts exactly `"npm"`
(default) or `"bun"` — `config/load.ts`'s `buildCi` rejects anything else at
config-load time. This is deliberate: `PACKAGE_MANAGER` (`render.ts`) is a
lookup table of install/exec commands + (for GitLab) a base image per
manager, and a bun repo has no `package-lock.json` for `npm ci` to read. A
wrong or unsupported value here would otherwise render CI that silently dies
at its own install step instead of failing loudly where the mistake was
made — at config load.

## Template engine

`renderTemplate`/`renderString` (`templates.ts`) is `{{key}}` substitution,
single pass, over files in `templates/ci/*.yml`. The placeholder pattern
(`(?<!\$)\{\{...\}\}`) has a negative lookbehind for `$` specifically so it
never matches GitHub Actions' own `${{ ... }}` expression syntax inside a
rendered template. A composed block (e.g. the verify-job fragment) must
already be fully rendered before being passed in as a value — a placeholder
inside a substituted value is never re-scanned. Throws if a template
references a key the caller didn't supply, rather than leaving a literal
`{{key}}` in rendered output.
